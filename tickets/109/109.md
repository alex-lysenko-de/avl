Механизм обновления: update.bat + update.ps1, режим --migrate.

Контекст: см. `wiki/update_workflow.md`. На этапе разработки отдельный Updater.exe не используется (документ §53) — обновление выполняется через `update.bat` → `update.ps1`.

Что сделать:
* `deployment/update.bat` — точка входа для пользователя (ярлык «Update Client»), запускает PowerShell без требования менять ExecutionPolicy системы (`-NoProfile -ExecutionPolicy Bypass -File update.ps1`), проверяет результат и показывает понятное сообщение при ошибке;
* `deployment/update.ps1` — реализует последовательность из документа (§21, §49): проверить, что приложение не запущено → прочитать локальный `version.txt` → запросить latest GitHub Release → прочитать `manifest.json` → скачать ZIP → проверить SHA-256 → backup базы → распаковать во временный staging-каталог → заменить файлы приложения → запустить `avl_docs.exe --migrate` → записать новый `version.txt` → удалить временные файлы → запустить приложение; каждый запуск пишет лог в `logs/update_<timestamp>.log`;
* `--migrate` режим в `avl_docs/app/main.py` (или отдельная точка входа): без GUI, применяет миграции Alembic к текущей базе, возвращает exit code 0/≠0;
* `alembic.ini` + пустой каталог `migrations/` (готовы для будущих миграций схемы — сами миграции вне рамок этого тикета);
* backup базы перед миграцией — по аналогии с уже описанным в readme.md разделом 14 форматом (`database_<timestamp>.sqlite.zip`).

Не входит в рамки тикета: конкретные миграции схемы (Client/Vehicle/Inspection — будущие тикеты), реальная синхронизация backup с Google Drive (папка backup только создаётся локально).

Зависит от тикета 108 (формат ZIP/manifest.json/version.txt).
