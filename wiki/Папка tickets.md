# Папка `tickets`

Файловое хранилище тикетов для ИИ-агента (Claude Code), который в этом проекте может выполнять роли разработчика, архитектора и ревьювера. Расположена в корне репозитория: `tickets/`.

Не путать с [[Процесс разработки|Trello]] — Trello предназначен для коммуникации между заказчиком и разработчиком, а `tickets/` это отдельный, файловый механизм постановки задач именно для ИИ-агента.

## Структура

```text
tickets/
├── readme.md          — описание папки и общие правила работы с тикетами
├── dashboard.yaml      — компактный список всех тикетов (id, title, status)
├── 099/
│   ├── 099.md          — текст тикета
│   └── status.txt      — текущий статус
├── 100/
│   ├── 100.md
│   └── status.txt
└── 101/
    ├── 101.md
    └── status.txt
```

Каждый тикет — это отдельная папка, названная номером тикета (например `099`). Внутри:

* `<номер>.md` — текст задачи (может содержать описание, дополнительные детали, ссылки, вставленные фрагменты); при существенном пересмотре тикета этот файл обновляется до актуальной формулировки;
* `status.txt` — текущий статус тикета одним словом/фразой (источник истины для этого тикета);
* `readme.md` — необязательный файл с дополнительной информацией: заметки, история пересмотра, причины отмены и т. п. Создаётся только когда есть что туда писать — не для каждого тикета;
* при необходимости — дополнительные файлы, относящиеся к тикету (скриншоты, приложения и т. п.).

## `dashboard.yaml`

Компактный агрегированный обзор всех тикетов — список записей `id` / `title` / `status`, без лишних полей (по возможности без замечаний, зависимостей и т. п. — это сознательно оставлено в `readme.md` тикета, чтобы дашборд оставался коротким и не дублировал подробности). Обновляется синхронно с `status.txt` при каждом изменении статуса — `status.txt` остаётся источником истины для конкретного тикета, `dashboard.yaml` лишь отражает его.

## Статусы

Наблюдаемые в проекте значения `status.txt` / `dashboard.yaml`:

* `NEW` / `new` — тикет создан, работа не начата;
* `IN_PROGRESS` / `in_progress` — тикет в работе;
* `DONE` / `done` — тикет полностью выполнен;
* `CANCELLED` / `cancelled` — тикет отменён (актуальность задачи отпала, например из-за пересмотра архитектуры другим тикетом или документом).

Список не является жёстко фиксированным (в `tickets/readme.md` упоминается также промежуточный статус ожидания ответа заказчика/пользователя по аналогии с Trello-схемой `WAITING FOR CUSTOMER`), но именно `NEW → IN_PROGRESS → DONE` — базовый жизненный цикл.

## Как пользователь ставит задачи

Пользователь может управлять тикетами голосовыми или текстовыми командами, например: создать тикет, закрыть тикет, начать работу над тикетом, обновить документацию согласно тикету и т. д.

## Общие правила работы с тикетами (из `tickets/readme.md`)

1. **Не формировать требования, если задача неоднозначна.** Сначала оценить, достаточно ли информации для реализации.
2. **Если информации недостаточно** — задавать только уточняющие вопросы, влияющие на реализацию (не «ради вопросов»); если есть несколько вариантов реализации — перечислить их и попросить пользователя выбрать.
3. **Не делать важных предположений самостоятельно** — всё, что может повлиять на реализацию, выносится на согласование с пользователем.
4. **Разделять информацию на четыре категории:** подтверждённые требования, предположения, открытые вопросы, рекомендации.
5. **Формат уточняющих вопросов** должен быть удобен для голосового и клавиатурного ввода: у каждого вопроса — идентификатор (`[Q1]`, `[Q2]`…), у каждого варианта ответа — идентификатор (`[v1]`, `[v2]`, `[y/n]`). Пользователь должен иметь возможность ответить короткой фразой («Вопрос 1, вариант 2») или короткой строкой с клавиатуры (`Q1v2 Q3y Q4:текст`). Наиболее предпочтительный вариант помечается как «рекомендуется».

Эти правила также продублированы в `CLAUDE.md` в корне репозитория, как того явно требует `tickets/readme.md`.
