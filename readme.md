# Описание проекта и технической инфраструктуры

## 1. Общая задача проекта

Разрабатывается локальное Windows-приложение или набор связанных Python-приложений для работы с документами Microsoft Word, PDF и данными клиентов.

Основные функции проекта:

* заполнение существующих шаблонов Microsoft Word;
* генерация документов на основании данных;
* работа с PDF;
* различные вспомогательные утилиты для обработки текста и документов;
* ведение базы данных клиентов;
* хранение информации об автомобилях;
* хранение результатов проверок;
* выполнение проверок и бизнес-правил;
* формирование итоговых документов;
* постепенное расширение функциональности по мере развития проекта.

Проект начинается как локальное приложение для одного пользователя на одном Windows-компьютере.

В дальнейшем возможна необходимость перехода к централизованной базе данных и работе нескольких точек/пользователей. Эта возможность должна учитываться при проектировании архитектуры, но **не должна усложнять первую версию проекта**.

---

# 2. Пользователи

На начальном этапе:

* 1 разработчик;
* 1 заказчик;
* 1 пользователь приложения;
* 1 Windows-компьютер заказчика;
* полностью локальная работа приложения.

Разработчик работает на собственном компьютере и имеет полный набор инструментов разработки.

Заказчик не должен заниматься разработкой и не должен устанавливать:

* Python;
* Git;
* IDE;
* виртуальное окружение;
* Docker;
* SQLite Server;
* инструменты сборки.

На компьютере заказчика должно быть установлено только то, что необходимо для работы готового приложения и Microsoft Word.

---

# 3. Основной принцип разработки

Проект не использует полноценную методологию Scrum.

Используется упрощённый итеративный процесс:

1. Разработчик получает задачу или вопрос.
2. Задача фиксируется в тикет-трекере.
3. Разработчик реализует изменение.
4. Изменение отправляется в GitHub.
5. Автоматически запускается сборка и тестирование.
6. При успешной сборке новая версия становится доступна заказчику.
7. Заказчик тестирует результат.
8. Заказчик оставляет комментарий, подтверждает выполнение либо создаёт новую задачу/возвращает тикет на доработку.

Основной принцип:

**изменение → автоматическая сборка → доступная заказчику версия → проверка заказчиком.**

Не требуется сложное управление спринтами, velocity, story points и другими Scrum-механиками.

---

# 4. Репозиторий и контроль версий

Используется:

**Git + GitHub.**

GitHub является основной системой хранения исходного кода.

Репозиторий содержит:

* исходный код;
* тесты;
* конфигурацию проекта;
* Word-шаблоны, если они являются частью программного продукта;
* миграции базы данных;
* документацию;
* настройки CI/CD;
* скрипты сборки;
* конфигурацию упаковки приложения.

Git используется только разработчиком.

На компьютере заказчика Git не устанавливается.

Заказчик не работает непосредственно с Git repository.

---

# 5. CI/CD и автоматическая сборка

После `git push` должна автоматически запускаться GitHub Actions.

Базовый pipeline:

```text
git push
    ↓
GitHub Actions
    ↓
установка Python и зависимостей
    ↓
автоматические тесты
    ↓
сборка Windows-приложения
    ↓
создание готового пакета
    ↓
публикация артефакта
    ↓
доступность новой версии заказчику
```

Если автоматические тесты или сборка не проходят, новая версия не должна становиться доступной заказчику.

Таким образом, `git push` является основным событием, запускающим процесс доставки новой версии.

---

# 6. Формат приложения

Приложение должно поставляться заказчику как готовое Windows-приложение.

Python и зависимости должны быть включены в распространяемую сборку.

Предпочтительный формат:

* один основной `.exe`;
* либо несколько `.exe`, если функциональность целесообразно разделить на отдельные утилиты;
* общий механизм обновления для всех компонентов.

Предварительно предполагается использование PyInstaller или аналогичного инструмента упаковки Python-приложения.

Конкретный инструмент упаковки будет выбран на этапе реализации.

---

# 7. Установка

Для первоначальной установки используется отдельный installer.

Заказчик запускает установщик один раз.

Установщик автоматически:

* устанавливает приложение;
* устанавливает необходимые файлы;
* создаёт структуру каталогов;
* создаёт ярлык;
* устанавливает Updater;
* выполняет необходимые первоначальные настройки.

После первоначальной установки заказчику не требуется вручную копировать файлы приложения.

---

# 8. Автоматическое обновление

В приложении должен присутствовать отдельный компонент:

**Updater.**

Updater отвечает за получение и установку новых версий приложения.

Основной сценарий:

```text
Пользователь запускает приложение
        ↓
Приложение проверяет наличие новой версии
        ↓
Найдена новая версия
        ↓
Пользователь нажимает "Обновить"
        ↓
Основное приложение закрывается
        ↓
Updater скачивает новую сборку
        ↓
Проверяет целостность файлов
        ↓
Заменяет файлы приложения
        ↓
Запускает новую версию
```

Updater должен быть отдельным executable, поскольку работающая программа не должна пытаться самостоятельно заменять собственный `.exe`.

---

# 9. Google Drive

У заказчика уже используется Google Drive.

Google Drive планируется использовать для:

* резервного копирования базы данных;
* хранения архивов;
* возможно, хранения дополнительных файлов проекта;
* при необходимости, хранения дистрибутивов или промежуточных сборок.

Предпочтительный способ работы с backup:

```text
локальная база
      ↓
создание backup
      ↓
папка Google Drive
      ↓
автоматическая синхронизация Google Drive
```

Если Google Drive for Desktop доступен на компьютере заказчика, приложение по возможности должно использовать обычную синхронизируемую папку, без необходимости самостоятельно реализовывать Google Drive API.

---

# 10. Google Drive и обновления

Google Drive рассматривается как возможный источник файлов обновления, однако механизм обновления не должен зависеть непосредственно от того, насколько быстро Google Drive синхронизировал файлы.

Предпочтительная архитектура:

```text
GitHub
   ↓
GitHub Actions
   ↓
готовая сборка
   ↓
источник дистрибутива
   ↓
Updater
   ↓
компьютер заказчика
```

Google Drive может использоваться как хранилище дистрибутива, но окончательная схема доставки обновлений должна быть выбрана после проверки надёжности синхронизации.

Не следует обновлять работающую программу простым копированием файлов через Google Drive без отдельного контроля версий и механизма проверки целостности.

---

# 11. База данных

На начальном этапе используется:

**SQLite.**

Причины:

* один пользователь;
* один компьютер;
* локальная работа;
* отсутствие необходимости в сервере;
* отсутствие необходимости устанавливать отдельный database server;
* простое резервное копирование;
* возможность дальнейшей миграции на PostgreSQL или другую серверную БД.

SQLite-файл хранится отдельно от файлов приложения.

Например:

```text
ClientApp/
    application/
    updater/
    templates/
    data/
        database.sqlite
```

Рабочая база данных не хранится в Git repository.

---

# 12. Структура базы данных

База должна быть спроектирована как нормальная реляционная модель.

Предварительно предполагаются сущности:

* Client;
* Vehicle;
* Inspection;
* InspectionItem;
* InspectionResult;
* Document;
* другие сущности по мере уточнения предметной области.

Не следует создавать одну большую таблицу со всеми данными клиента, автомобиля и проверок.

Необходимо предусмотреть:

* связи между сущностями;
* историю проверок;
* возможность повторных проверок;
* ограничения целостности;
* миграции схемы.

---

# 13. Миграции базы данных

Структура SQLite не должна изменяться вручную.

При изменении схемы используются миграции.

Например:

```text
schema 1
   ↓
migration 002
   ↓
schema 2
   ↓
migration 003
   ↓
schema 3
```

При обновлении приложения оно должно при необходимости автоматически обновлять структуру существующей базы.

Рабочая база заказчика не должна заменяться новой пустой базой при обновлении программы.

---

# 14. Резервное копирование

Резервное копирование базы является обязательной функцией.

Должна существовать возможность:

* создать backup вручную;
* создавать backup автоматически;
* восстановить базу из backup;
* хранить несколько предыдущих копий.

Предварительный формат:

```text
Backups/
    database_2026-08-09_103000.sqlite.zip
    database_2026-08-08_103000.sqlite.zip
    ...
```

Папка backup может находиться внутри синхронизируемой Google Drive директории.

GitHub не используется как основное хранилище рабочих SQLite backup-файлов.

Причины:

* база может содержать персональные данные;
* Git хранит историю изменений;
* бинарная SQLite база плохо подходит для Git;
* backup и version control имеют разные задачи.

# 15. Конфиденциальность данных

В базе могут находиться персональные и чувствительные для бизнеса данные:

* ФИО;

* контактные данные;
* данные автомобилей;
* VIN;

Такие данные не должны попадать в публичный Git repository.

Исходный код и пользовательские данные должны быть разделены.

# 18. Тикет-трекер

Используется:

**Trello.**

Другие системы на данном этапе не рассматриваются.

Требования к тикет-трекеру:

* не российская разработка;
* бесплатный тариф;
* простой современный интерфейс;
* русский язык;
* минимальное количество сущностей;
* обычный список задач/карточек;
* статус задачи;
* комментарии;
* вложения;
* изображения;
* возможность вставлять скриншоты через Ctrl+V;
* возможность прикладывать файлы;
* желательно поддержка видео;
* возможность работы через web;
* наличие API для будущей автоматизации;
* возможность дальнейшей интеграции с AI-агентами.

Не требуется:

* полноценный Scrum;
* сложные Kanban-процессы;
* story points;
* velocity;
* сложная иерархия проектов;
* корпоративная система управления проектами.

Предполагаемый минимальный workflow:

```text
TODO
  ↓
IN PROGRESS
  ↓
REVIEW
  ↓
DONE
```

При необходимости может использоваться дополнительный статус:

```text
WAITING FOR CUSTOMER
```

# 19. Использование AI-агентов

Разработчик планирует использовать Claude code в качестве основного ИИ-агента
Поєтому в будущем желательно предусмотреть возможность подключения AI-агента к тикет-трекеру и GitHub.

Потенциальные функции AI-агента:

* создавать тикеты;
* анализировать сообщения заказчика;
* преобразовывать описание проблемы в структурированную задачу;
* классифицировать задачу как bug / feature / question;
* добавлять описание и acceptance criteria;
* роль архитектора: ticket.txt + уточняющая информация => implementation_plan.md
* роль кодера: implementation_plan.md => code + implementation_report.md + git commit
* роль ревьювера : ticket.txt + уточняющая информация + implementation_plan.md + git diff + implementation_report.md => code_review
* анализировать вложенные изображения;
* читать существующие тикеты;
* искать связанные задачи;
* анализировать Git repository;
* создавать предложения по исправлению;
* в перспективе создавать branch и pull request.

Поэтому при выборе технических решений необходимо учитывать наличие API.

```text
Разработчик
    ↓

    ↓
автоматические тесты
    ↓

    ↓
публикация
```

# 23. Возможное будущее развитие

Если проект вырастет до нескольких точек или нескольких пользователей, архитектура должна позволять перейти от:

```text
Windows Application
      ↓
SQLite
```

к:

```text
Windows/Web Application
      ↓
API
      ↓
PostgreSQL
```

При этом локальная SQLite-база является решением только для начального этапа.

Переход на централизованную БД не должен требовать полного переписывания бизнес-логики приложения.

# 24. Главный принцип архитектуры

Архитектура должна быть максимально простой на начальном этапе.

Нельзя добавлять инфраструктурные компоненты только потому, что они "могут когда-нибудь пригодиться".

На первом этапе система должна решать задачу:

```text
Разработчик
    ↓
Git push
    ↓
Автоматическая сборка
    ↓
Автоматическая доставка
    ↓
Заказчик тестирует
    ↓
Тикет / комментарий
    ↓
Следующее изменение
```

При этом:

```text
GitHub = код и CI/CD
Trello = коммуникация и задачи
Google Drive = пользовательские данные и backup
SQLite = локальная БД
Updater = доставка обновлений
Windows Application = конечный продукт
```

Это является текущим техническим baseline проекта.
